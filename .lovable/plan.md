# المرحلة الخامسة — «التوصيل الخاص»

## لماذا هذه المرحلة بالذات
ترتيب الخارطة المعتمد في المشروع: المطاعم → المتاجر → المهن والخدمات → طلب مندوب → **التوصيل الخاص** → التكسي → الدفع الإلكتروني → OTP.
ما تم فعلاً: المطاعم، المتاجر، الخدمات والمهن، وطلب مندوب مستقل (`/courier`).

المؤشرات الموجودة داخل المشروع نفسه:
- جدول `services` فيه خدمة مفعّلة **«التوصيل الخاص»** (`route_path = /special-delivery`، أيقونة `PackageCheck`، قسم التوصيل، ترتيب 2) ولا توجد لها أي صفحة.
- `order_type` enum يحتوي `special_delivery` أصلاً، ولا توجد له أي قاعدة تسعير ولا دالة إنشاء.
- `src/lib/orders.ts` فيه `isCourierType()` يعامل `special_delivery` مثل `courier` مؤقتاً — أي أن المسار محجوز ولم يُبنَ.

إذن المرحلة الخامسة = **التوصيل الخاص**.

## الفرق عن «اطلب مندوب» (لتفادي تكرار نظام)
`courier` = مشوار فوري صغير، نقطة → نقطة، توزيع فوري.
`special_delivery` = مهمة توصيل مُهيّأة مسبقاً: نوع مركبة (دراجة/سيارة/بيك أب/شاحنة صغيرة)، حجم/وزن تقريبي، موعد الآن أو مجدول، احتمال نقاط تسليم متعددة، وأجرة تعتمد على نوع المركبة إضافة للمسافة.

## النطاق

### الصفحات
- `/special-delivery` — إنشاء الطلب: اختيار نوع المركبة، نقطة الاستلام، نقطة/نقاط التسليم، وصف الحمولة والوزن التقريبي، الآن أو موعد مجدول، عرض تسعيرة مباشرة من الخادم قبل التأكيد.
- `/special-delivery/quote` (ضمن نفس الصفحة كخطوة، لا مسار منفصل) — ملخص السعر والتفاصيل قبل الإرسال.
- التتبع: إعادة استخدام `/orders` و`/orders/$id` كما هي مع تسميات حالات خاصة.
- المندوب: إعادة استخدام `/driver` مع إظهار نوع المركبة والحمولة والموعد المجدول في بطاقة العرض.
- الإدارة: توسيع `/admin/courier` إلى تبويبين (مندوب / توصيل خاص) بدل صفحة جديدة.
- ربط بطاقة الخدمة الموجودة في الصفحة الرئيسية بالمسار الجديد.

### الخلفية وقاعدة البيانات
| التغيير | السبب |
|---|---|
| `vehicle_type` enum (`bike`, `car`, `pickup`, `small_truck`) + عمود `vehicle_type` و`scheduled_at` و`cargo_description` و`cargo_weight_kg` على `orders` | خصائص المهمة الخاصة |
| جدول `order_stops` (طلب، ترتيب، إحداثيات، نص العنوان، هاتف المستلم) لنقاط التسليم المتعددة | تسليم لأكثر من نقطة |
| صفوف `pricing_rules` لنوع `special_delivery` لكل نوع مركبة (عمود `vehicle_type` اختياري على القاعدة) + fallback آمن | تسعير صحيح، حالياً لا توجد أي قاعدة لهذا النوع |
| دالة `create_special_delivery_order` (SECURITY DEFINER) تحسب المسافة الكلية عبر `haversine_km` عبر كل النقاط وتحسب الأجرة من القواعد | لا ثقة بأي سعر من الواجهة |
| دالة `quote_special_delivery` للتسعيرة قبل الإنشاء | عرض السعر بدون إنشاء طلب |
| توسيع `is_allowed_transition` لنوع `special_delivery` بنفس دورة `courier` | منع القفزات |
| `worker_profiles.vehicle_type` + تصفية المرشحين في `runDispatch` حسب نوع المركبة المطلوبة | لا يُعرض طلب بيك أب على دراجة |
| الطلبات المجدولة: لا تُوزّع إلا قرب موعدها — تُترك `scheduled` ويلتقطها الـ cron الحالي | جدولة فعلية |

### يُعاد استخدامه كما هو
- دورة الطلب `orders` / `order_status_history` وكل الحالات، و`change_order_status`.
- محرك التوزيع `src/lib/dispatch.server.ts`، جدول `delivery_offers`، القبول الذري `accept_delivery_offer`، الرفض وإعادة التوزيع.
- صيانة cron الحالية (انتهاء العروض + إعادة التوزيع) مع إضافة التقاط الطلبات المجدولة.
- تتبع `worker_locations` والخصوصية الحالية، والتقييمات، والإشعارات.
- منتقي الموقع في `/courier` و`/checkout` كمرجع للواجهة، ومكوّنات `app-shell` وتنسيق RTL الحالي.
- `COURIER_STATUS_FLOW` مع تسميات خاصة بالتوصيل الخاص.

### بيانات seed
قواعد تسعير لبغداد لكل نوع مركبة، بدون أي مساس ببيانات المراحل السابقة.

## خارج نطاق المرحلة الخامسة
التكسي، الدفع الإلكتروني، OTP، تقسيم الأجرة بين نقاط متعددة على المستلمين، عقود الشركات/الحسابات التجارية، تتبّع خارجي عبر خرائط طرف ثالث.

## نقطة تحتاج تأكيدك
هل تريد **نقاط تسليم متعددة** ضمن هذه المرحلة، أم نكتفي بنقطة استلام واحدة ونقطة تسليم واحدة مع نوع مركبة وجدولة (وتأجيل التعدد لاحقاً)؟ التعدد يضيف جدول `order_stops` وتعقيد تسعير إضافي.
